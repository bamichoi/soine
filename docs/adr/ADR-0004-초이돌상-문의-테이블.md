# ADR-0004: 초이돌상 문의 테이블

- 날짜: 2026-11-23
- 상태: 제안
- 작성자: 팀

## 배경 (Context)

초이돌상 백오피스에서 고객 문의를 모아 보고, 예약 확정 여부를 관리해야 한다.
기존 메뉴 "상담"은 "문의"로 이름을 바꾼다.

## 결정 (Decision)

1. `choidolsang.inquiries` 테이블을 만든다.

   | 컬럼                   | 타입                 | 필수 | 설명                |
   | ---------------------- | -------------------- | ---- | ------------------- |
   | `id`                   | UUID                 | ✓    | 내부 식별자         |
   | `code`                 | VARCHAR(16), UNIQUE  | ✓    | 문의 번호. 8자리 무작위 코드 (예: `7K3FQ9AM`) |
   | `inquiredOn`           | DATE                 | ✓    | 문의 날짜. 문의 내용 로그 첫 기록의 날짜와 같게 유지 (목록 정렬용) |
   | `desiredReservationAt` | TIMESTAMPTZ          |      | 희망 예약 날짜·시간 |
   | `location`             | VARCHAR(200)         |      | 장소                |
   | `desiredConceptId`     | UUID (FK)            |      | 희망 돌상 컨셉 (`concepts.id`, 같은 스키마) |
   | `status`               | `inquiry_status`     | ✓    | 상태, 기본값 `pending` |
   | `rejectionReason`      | TEXT                 |      | 거절 사유. 거절 상태일 때만 값이 있음 |
   | `deletedAt`            | TIMESTAMPTZ          |      | 숨김 삭제 시각. 값이 있으면 어디서도 보이지 않음 |
   | `createdAt`, `updatedAt` | TIMESTAMPTZ        | ✓    |                     |

   문의 내용은 `choidolsang.inquiry_records` 테이블에 로그로 쌓는다. 첫 기록이 첫 문의이고,
   그 뒤로 같은 고객이 이어서 남긴 문의를 기록 하나씩 덧붙인다. 문의마다 기록이 1개 이상 있어야 한다.

   | 컬럼          | 타입        | 필수 | 설명 |
   | ------------- | ----------- | ---- | ---- |
   | `id`          | UUID        | ✓    | 내부 식별자 |
   | `inquiryId`   | UUID (FK)   | ✓    | 문의 (`inquiries.id`, 같은 스키마) |
   | `recordedOn`  | DATE        | ✓    | 기록 날짜 |
   | `content`     | TEXT        | ✓    | 기록 내용 (최대 5000자) |
   | `createdAt`   | TIMESTAMPTZ | ✓    | 같은 날짜 기록의 순서를 정한다 |

   - 로그는 기록 날짜, 같은 날짜면 등록 순으로 정렬한다.
   - 기록을 추가·수정하면 같은 트랜잭션에서 문의 행을 잠그고 `inquiredOn`을 첫 기록 날짜로 맞춘다.
   - 문의와 문의 로그 기록은 지우지 않는다(2026-11-25 변경). 처음에는 기록 완전 삭제와 문의 숨김 삭제가 있었으나,
     기록을 남기기 위해 삭제 API를 모두 없앴다. 잘못 적은 내용은 수정한다.
   - 처음에는 첫 문의 내용을 `inquiries.content`에 두었으나, 첫 문의도 로그의 한 항목으로 다루기로 하면서
     기록 테이블로 옮기고 컬럼을 지웠다 (마이그레이션 `move_choidolsang_inquiry_content_to_records`).

2. 상태는 `choidolsang.inquiry_status` enum으로 둔다: `pending`(대기), `confirmed`(예약확정), `rejected`(거절),
   `cancelled`(취소). 취소는 예약확정 후 연결된 예약이 취소되면 그 문의가 바뀌는 상태로,
   문의를 추가할 때는 고를 수 없다. 예약 기능에서 예약 취소와 함께 처리할 예정이다.
3. 희망 예약 일시는 시각대를 포함해 저장하고, 백오피스에서는 한국 시간(Asia/Seoul)으로 표시한다.
4. 희망 돌상 컨셉은 돌상 컨셉(`concepts`)을 참조한다 (ADR-0005).
   - 처음에는 자유 입력 문자열(`desiredConcept`)이었다. 마이그레이션 `link_choidolsang_inquiry_desired_concept`에서
     컨셉 이름과 정확히 같은 값(앞뒤 공백·대소문자 무시)만 그 컨셉으로 잇고, 나머지는 비운 뒤 글 컬럼을 지웠다.
   - 새로 고를 때는 숨김 삭제되지 않은 컨셉만 고를 수 있다(아니면 400). 이미 고른 컨셉은 그사이 삭제돼도 유지되며,
     응답의 `desiredConcept.isDeleted`로 표시한다. 컨셉은 숨김 삭제라 외래키는 `ON DELETE RESTRICT`로 둔다.
   - 검색(`field=desiredConcept`)은 컨셉 이름 부분 일치, 정렬은 컨셉 이름순이다.
     컨셉이 없는 문의는 오름차순에서 뒤, 내림차순에서 앞에 온다.
5. 화면과 URL에서는 UUID 대신 문의 번호(`code`)를 쓴다. 문의 건수나 순서가 드러나지 않도록
   헷갈리는 글자(I, L, O, U)를 뺀 Crockford Base32 8자리 무작위 코드로 만들고, 겹치면 다시 생성한다.
   순서가 없는 값이므로 정렬 대상에서 뺀다.
6. API (모두 초이돌상 관리자 세션 필수)
   - `GET /admin/choidolsang/inquiries` — 목록, 20건씩
     - `page`: 페이지 (기본 1)
     - `field`: 검색 항목 `all`(기본) | `code` | `content` | `location` | `desiredConcept`
     - `q`: 검색어 (최대 100자). 글자 항목은 부분 일치(대소문자 무시), 문의 번호는 부분 일치(대소문자 무시).
     - `status`: 상태 필터 `pending` | `confirmed` | `rejected` | `cancelled`. 검색어와 따로 고른다
       (처음에는 상태를 검색 항목으로 찾았으나 필터로 바꿨다).
     - `sort`: `inquiredOn`(기본) | `desiredReservationAt` | `location` | `desiredConcept` | `status`
     - `order`: `asc` | `desc`(기본). 빈 값은 맨 뒤, 같은 값은 최근 등록 순.
   - `GET /admin/choidolsang/inquiries/:code` — 상세 (대소문자 무시), 없으면 404
   - `POST /admin/choidolsang/inquiries` — 추가
     - 필수: `inquiredOn`(YYYY-MM-DD), `content`(최대 5000자). `content`는 로그의 첫 기록이 된다.
     - 선택: `desiredReservationAt`(시간대 포함 ISO 8601), `location`(최대 200자), `desiredConceptId`(돌상 컨셉 UUID),
       `status`(`pending`|`confirmed`|`rejected`, 기본 `pending`), `rejectionReason`(상태가 `rejected`이면 필수, 최대 1000자, 그 외엔 무시).
       빈 문자열은 null로 저장.

   ```json
   {
     "items": [{ "id": "…", "code": "7K3FQ9AM", "inquiredOn": "2026-11-20", "content": "…",
                 "desiredReservationAt": "2026-12-05T02:00:00.000Z",
                 "location": "…", "status": "pending",
                 "desiredConcept": { "id": "…", "name": "한복 클래식", "isDeleted": false } }],
     "pagination": { "page": 1, "pageSize": 20, "total": 45, "totalPages": 3 }
   }
   ```

   - `POST /admin/choidolsang/inquiries/:code/reject` — `{ reason }`(필수, 최대 1000자). 대기 → 거절.
   - `POST /admin/choidolsang/inquiries/:code/reopen` — 거절 → 대기, 거절 사유는 지운다.
   - 상태 전환은 현재 상태를 조건으로 갱신해 동시에 눌러도 한 번만 반영된다. 허용되지 않은 전환은 409.
   - 예약확정(`confirmed`) 전환은 예약 폼(예약 진행)에서 처리할 예정이다.
     예약확정 문의의 "예약 정보"는 예약 기능이 생기면 해당 예약으로 연결한다.
   - `PATCH /admin/choidolsang/inquiries/:code` — 수정. `desiredReservationAt`, `location`, `desiredConceptId`를
     모두 보낸다. 상태와 문의 날짜·내용(로그)은 바꾸지 않는다.
     `rejectionReason`은 거절된 문의일 때만 반영한다. 읽은 상태를 조건으로 갱신해 그사이 상태가 바뀌면 409.
   - `POST /admin/choidolsang/inquiries/:code/records` — 로그에 기록 추가 `{ recordedOn, content }`
   - `PATCH /admin/choidolsang/inquiries/:code/records/:recordId` — 기록 수정 `{ recordedOn, content }`
   - 기록 API는 모두 갱신된 문의 상세를 돌려준다. 다른 문의의 기록 ID는 404.
   - 목록의 `content`는 첫 기록 내용이고, 문의 내용 검색은 로그의 모든 기록에서 찾는다.
   - 상세에는 `records`(로그 전체, 오래된 것부터)가 함께 온다.
   - 문의 삭제 API는 없다. `deletedAt` 컬럼은 남아 있고, 값이 있는 문의는 계속 없는 문의(404)로 취급한다.
7. 관리자 API는 `AdminSessionGuard` + `@RequireAdminService('<service>')`로 보호한다.
   세션 미들웨어가 `admin/<service>/*` 경로별로 붙으므로 컨트롤러 경로와 서비스가 같아야 한다.

## 대안 (Alternatives)

1. 희망 날짜와 시간을 별도 컬럼으로 분리
2. 희망 돌상 컨셉을 처음부터 컨셉 테이블 참조로 설계

## 대안 기각 이유

1. 날짜만 알고 시간은 모르는 문의가 생기면 그때 분리를 검토한다. 지금은 하나의 일시로 충분하다.
2. 돌상 컨셉 데이터 구조가 아직 정해지지 않았다.

## 영향 (Consequences)

### 장점

1. 문의 목록을 백오피스에서 바로 조회할 수 있다.

### 단점/리스크

1. 문의 내용 수정·삭제, 예약 진행(예약확정 전환)은 아직 없다.
2. 희망 돌상 컨셉이 자유 입력이라 표기가 제각각일 수 있다.

## 롤백/재검토 조건

1. 문의가 예약으로 전환되는 흐름을 설계할 때
