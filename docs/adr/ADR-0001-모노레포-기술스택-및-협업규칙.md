# ADR-0001: 모노레포 기술 스택 및 협업 규칙

- 날짜: 2026-11-23
- 상태: 제안
- 작성자: 팀

## 배경 (Context)

초이돌상 고객 서비스, 초이돌상 백오피스, 끼루 백오피스를 함께 개발한다.
기존 JunSem 프로젝트에서 검증된 스택과 협업 규칙을 그대로 재사용해 초기 세팅 비용을 줄인다.

## 결정 (Decision)

1. 저장소 구조는 pnpm workspace 모노레포를 채택한다.
2. 기술 스택은 Next.js 16(프론트엔드·백오피스), NestJS 11(백엔드), Prisma 7, PostgreSQL 17로 한다.
3. API 방식은 REST로 통일하고 `packages/api-contract`의 OpenAPI 계약을 유지한다.
4. 앱 간 직접 import를 금지하고 API 통신만 허용한다.
5. 공통 코드는 `packages/shared`에 두되, 비즈니스 로직 공유는 금지한다.
6. 린트/포맷은 Biome으로 통일한다.
7. 주요 변경(API 계약, DB 스키마, 배포 구조)은 ADR로 기록한다.
8. 배포 인프라는 이 ADR 범위에서 제외하고, 배포 방식을 정할 때 별도 ADR로 기록한다.

## 대안 (Alternatives)

1. 서비스별 멀티레포
2. GraphQL 또는 tRPC

## 대안 기각 이유

1. 백엔드와 계정 체계를 공유하므로 멀티레포는 변경 추적과 AI 컨텍스트 공유 비용이 크다.
2. 현재 목표(빠른 시작, 명확한 계약) 대비 운영 복잡도가 증가한다.

## 영향 (Consequences)

### 장점

1. JunSem과 같은 규칙과 도구를 써서 팀이 바로 작업할 수 있다.
2. REST/OpenAPI 계약으로 프론트-백 변경 충돌을 줄인다.

### 단점/리스크

1. 모노레포가 커지면 CI 시간이 늘어날 수 있다.
2. 두 서비스(초이돌상, 끼루)의 코드가 한 백엔드에 섞일 수 있다. 모듈 경계로 분리한다.

## 적용 범위 (Scope)

본 저장소 전체

## 롤백/재검토 조건

1. 끼루가 독립 고객 서비스와 별도 계정 체계를 갖게 될 때
2. 모노레포 CI 병목이 심각할 때
