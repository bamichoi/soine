# ADR-0010: 끼루를 굿플레이스로 이름 변경

- 날짜: 2026-11-28
- 상태: 제안
- 작성자: 팀

## 배경 (Context)

중개 운영 도구의 서비스 이름이 '끼루(kkiru)'에서 '굿플레이스(goodplace)'로 바뀌었다.
화면 문구만 바꾸면 주소·API·DB·코드에 옛 이름이 남아 두 이름이 섞이고, 새로 들어오는 사람이 헷갈린다.
사용자가 화면 문구뿐 아니라 코드·주소·DB까지 모두 바꾸기로 승인했다.

## 결정 (Decision)

서비스 이름을 모든 층에서 바꾼다. 영어 이름은 `goodplace`(PascalCase `Goodplace`, 상수 `GOODPLACE`),
한국어 표시 이름은 '굿플레이스'다. 초이돌상(choidolsang)은 그대로 둔다.

1. 화면 문구: 메뉴, 제목, metadata title(`… | 굿플레이스`), 로그인 화면 서비스 탭, 빈 문구, aria-label.
2. 백오피스 주소: `/kkiru/*` → `/goodplace/*`, 로그인 쿼리 `?service=kkiru` → `?service=goodplace`.
   예전 북마크를 위해 `apps/backoffice/next.config.ts`에 `/kkiru/:path*` → `/goodplace/:path*`
   영구(308) 리다이렉트를 둔다.
3. API: `/admin/kkiru/*` → `/admin/goodplace/*`. 서비스 식별자(`ADMIN_SERVICES`)도 `goodplace`다.
   예전 API 경로는 남기지 않는다(백오피스 말고 쓰는 곳이 없다).
4. 코드 이름: 백엔드 모듈 `src/goodplace`, 클래스 `Goodplace*`, 파일 `goodplace-*`, 프론트 컴포넌트·lib 파일과 식별자.
5. DB: PostgreSQL 스키마 `kkiru` → `goodplace`, Prisma 모델 `Kkiru*` → `Goodplace*`.
   테이블·enum은 `@@map`으로 이름이 고정돼 있어 모델 이름을 바꿔도 테이블 이름은 그대로다.
6. 환경 변수: `KKIRU_*` → `GOODPLACE_*`.
7. 관리자 세션 쿠키: 서비스 이름에서 만들어지므로 `soine.kkiru.admin.sid` → `soine.goodplace.admin.sid`로 바뀐다.

### 마이그레이션

`20261128120000_rename_service_schema_to_goodplace`에서 다음 한 줄만 실행한다.

```sql
ALTER SCHEMA "kkiru" RENAME TO "goodplace";
```

- 테이블(관리자 계정 `admins`, 세션 `admin_sessions` 포함), enum, 인덱스, 제약, 데이터가 스키마를 따라 옮겨진다.
- 기존 마이그레이션 파일은 이력이므로 고치지 않는다. 새 DB에 처음부터 `migrate deploy`하면
  앞선 파일들이 `kkiru` 스키마를 만들고 채운 뒤, 마지막에 이 파일이 이름을 바꾼다.
- 기존 마이그레이션 디렉터리 이름과 SQL 안의 `kkiru`는 그대로 남는다.

## 대안 (Alternatives)

1. 화면 문구만 바꾸고 코드·주소·DB는 `kkiru`로 둔다.
2. 새 `goodplace` 스키마를 만들고 데이터를 복사한 뒤 `kkiru` 스키마를 지운다.
3. 예전 API 경로 `/admin/kkiru/*`를 별칭으로 함께 남긴다.

## 대안 기각 이유

1. 표시 이름과 코드 이름이 달라 계속 번역해야 하고, 사용자가 전체 변경을 원했다.
2. 복사·삭제는 데이터 삭제 위험이 있고, `ALTER SCHEMA ... RENAME`이 한 번에 원자적으로 끝난다.
3. API를 쓰는 곳은 백오피스 하나이고 함께 배포되므로 별칭이 필요 없다.

## 영향 (Consequences)

### 장점

1. 화면·주소·API·DB·코드의 서비스 이름이 하나로 맞는다.

### 단점/리스크

1. 세션 쿠키 이름이 바뀌어 기존 굿플레이스 관리자는 한 번 다시 로그인해야 한다.
   세션 행은 새 스키마로 옮겨지지만 브라우저가 옛 쿠키 이름으로 보내므로 쓰이지 않고, 만료되면 정리된다.
2. 운영 환경 변수 키(`KKIRU_*`)를 `GOODPLACE_*`로 바꾸지 않으면 값이 읽히지 않는다.
3. 마이그레이션 적용 전 옛 코드가 돌고 있으면 `goodplace` 스키마가 없어(또는 적용 후 옛 코드는 `kkiru`가 없어)
   요청이 실패한다. 배포 때 마이그레이션과 백엔드 재시작을 함께 한다.
4. `/login?service=kkiru`처럼 옛 쿼리로 들어오면 서비스 탭이 기본값(초이돌상)으로 열린다.

## 비용 (Cost)

### 산정 기준

1. 추가 인프라나 구독 없음. 개발·검토 시간만 든다.

### 예상 비용

1. 월 고정비: 0
2. 월 변동비: 0
3. 월 합계(예상): 0

### 민감도/변동 조건

1. 해당 없음.

## 완화 전략

1. 예전 백오피스 주소는 영구 리다이렉트로 새 주소에 넘긴다.
2. 배포 순서: 운영 env 키 변경 → `prisma migrate deploy` → 백엔드·백오피스 재시작.
3. 관리자에게 다시 로그인해야 한다고 미리 알린다.

## 적용 범위 (Scope)

`apps/backend`, `apps/backoffice`, `apps/backend/prisma`, 문서(AGENTS.md, README, ADR, docs/design), `.claude/agents`.
초이돌상(choidolsang)은 바꾸지 않는다.

## 롤백/재검토 조건

1. 되돌리려면 `ALTER SCHEMA "goodplace" RENAME TO "kkiru";` 마이그레이션을 새로 만들고 코드를 되돌린다.
2. 옛 주소로 들어오는 요청이 충분히 줄면 `/kkiru` 리다이렉트를 지울지 재검토한다.
