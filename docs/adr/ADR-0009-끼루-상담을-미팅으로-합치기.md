# ADR-0009: 끼루 상담을 미팅으로 합치기

- 날짜: 2026-11-28
- 상태: 제안
- 작성자: 팀

## 배경 (Context)

ADR-0008에서는 상담(고객 1명 + 상담매물 여러 개) → 미팅(매물 1건) → 계약(미팅 참조) 세 단계로 나눴다.
실제 업무에서는 상담과 미팅이 따로 구분되지 않고, 매물별 미팅을 하나씩 만드는 일이 번거로웠다.
상담 화면에서 매물을 고르거나 찾아 바로 계약으로 넘어가고 싶다는 요청이 있었다.

## 결정 (Decision)

1. **지금의 상담 구조를 그대로 '미팅'으로 부르고, 옛 미팅 엔티티는 없앤다.** 흐름은 미팅 → 계약 두 단계다.
   ADR-0008의 결정 1(테이블 중 상담·미팅 부분), 4(삭제 원칙의 예외), 5(상태), 6(계약 히스토리),
   7(상담매물), 8(일정)을 대체한다.

   | 테이블 | 내용 |
   | ------ | ---- |
   | `meetings` (옛 `consultations`) | 미팅. 케이스 번호, 고객, 제목, 희망 조건, 유입 경로, **미팅 일시(`meetAt`, 날짜+시간)**, **중단 시각(`stoppedAt`)**, 상태 |
   | `meeting_records` (옛 `consultation_records`) | 미팅 내용 로그. **종류(`kind`)**: 내용·중단 사유·재개 사유·계약취소 사유 |
   | `meeting_listings` (옛 `consultation_listings`) | 미팅 매물 (미팅 ↔ 매물, 여러 개) |
   | `contracts` | 계약. **미팅(`meetingId`) + 대상 매물(`listingId`, 필수, `ON DELETE RESTRICT`)** 과 기존 계약 항목 |

   - Prisma 모델: `KkiruMeeting`, `KkiruMeetingRecord`, `KkiruMeetingListing`, `KkiruContract`.
   - 상담 일자(`consultedOn`)는 없애고 미팅 일시로 바꾼다. 매물별 방문 일시는 두지 않는다.
   - 옛 `consultation_status` enum은 없애고 `meeting_status`(meeting, contracting, contracted,
     contract_cancelled, stopped)를 새로 만든다. 상담중(`consulting`)은 미팅중(`meeting`)이 된다.
   - API는 `/admin/kkiru/meetings`(주소는 케이스 번호)로 옮기고 `/admin/kkiru/consultations`는 없앤다.
     화면 주소 `/kkiru/consultations`도 리다이렉트 없이 없앤다.

2. 상태 (`apps/backend/src/kkiru/common/status-sync.ts`)
   - **미팅**: 완료 계약 있음 → 계약완료 > 계약중 계약 있음 → 계약중 > `stoppedAt` 있음 → 진행중단
     > 취소 계약만 있음 → 계약취소 > 그 외 미팅중.
   - **매물**: 그 매물의 완료 계약 → 계약완료 > 계약중 계약 → 계약중
     > 미팅중·계약취소 상태인 미팅의 미팅 매물 → 미팅중 > 계약가능.
   - 미팅 중단은 미팅중·계약취소 상태에서만, 사유를 로그(kind=stopped)에 남기고 `stoppedAt`을 채운다.
     재개는 사유(kind=resumed)를 남기고 `stoppedAt`을 비운 뒤 다시 계산한다.
   - 미팅 매물 추가·삭제 때는 그 매물만, 미팅 중단·재개와 계약 생성·완료·취소 때는 그 미팅의
     모든 미팅 매물과 계약 매물을 다시 계산한다. 미팅 상태를 먼저, 매물 상태를 나중에 맞춘다.
   - 잠금 순서는 미팅 → 계약 → 매물(매물끼리는 id 순)이다.
   - 미팅에 매물을 더하면 그 매물은 미팅중이 된다(다른 고객이 계약 중이면 계약중 그대로). 계약완료 매물은 더할 수 없다(409).
   - 계약이 걸린 미팅 매물은 뺄 수 없다(409). 계약이 없는 매물은 연결만 지운다.
3. 계약
   - 미팅 상세에서 미팅 매물을 고르거나 검색해 바로 계약을 만든다(`POST /admin/kkiru/contracts`
     `{ meetingCode, listingId, ... }`). 고른 매물이 미팅 매물에 없으면 같은 트랜잭션에서 더한다.
   - 미팅이 미팅중·계약취소 상태가 아니면 409. **한 미팅에 계약중 계약은 1건만, 계약완료 계약이 있으면
     새 계약 금지(409).** DB 제약이 아니라 계약 생성 때 검사한다.
   - 매물 행을 잠근 뒤 매물이 계약중·계약완료면 409.
   - 케이스 번호와 고객은 계약의 미팅에서 가져온다.
   - 계약 히스토리는 그 미팅의 로그만 보여 준다. 계약취소 사유는 미팅 로그(kind=contract_cancelled)에도 남긴다.
   - 매물 상세(`GET /admin/kkiru/listings/:code`, 수정 응답도 같음)는 이 매물이 미팅 매물로 걸린 미팅 목록 `meetings`
     (`code`·`title`·`customer.name`·`meetAt`·`status`, `contract`: 이 미팅에서 이 매물로 맺은 가장 최근 계약
     `{ id, status, contractedOn }` 또는 `null`)를 미팅 일시 내림차순으로, 계약취소 포함 전부 함께 준다.
4. 일정: 미팅은 미팅 일시와 미팅 제목으로 보여 주고 진행중단 미팅은 뺀다. 계약은 계약일과 대상 매물 이름으로
   보여 주고 취소된 계약은 뺀다. 잔금은 잔금일에 '잔금' 항목으로 보여 주고(계약 상세로 연결) 취소된 계약은 뺀다.
5. **끼루 데이터 삭제 금지 원칙의 예외**: 이 전환에서 옛 `meetings`·`meeting_records` 테이블과
   옛 `meeting_status`·`consultation_status` enum을 데이터 이전 뒤 지운다(사용자 승인).
   그 밖의 끼루 데이터는 계속 지우지 않는다.

### 데이터 이전 (마이그레이션 `20261128090000`~`20261128090400`)

1. 상담 로그에 `kind`(기본 note), 상담에 `stoppedAt`·`meetAt`, 계약에 `listingId`를 더한다.
2. 옛 미팅의 (상담, 매물)을 상담매물에 넣는다(이미 있으면 그대로). 옛 미팅 로그를 상담 로그로 복사한다
   (종류 유지, 내용 앞에 `[매물 이름] `). 옛 미팅마다 `[매물 이름] 미팅 일시 YYYY-MM-DD HH:mm`(한국 시각) 기록을 남긴다.
   미팅 일시 = 옛 미팅 중 가장 이른 미팅 일시, 없으면 상담 일자 00:00(한국 시각). 상담 일자는 지운다.
   계약의 `listingId`를 옛 미팅의 매물로 채우고 `meetingId`를 새 미팅(옛 상담) id로 바꾼다.
3. 옛 미팅 테이블과 enum을 지운 뒤(이름이 겹치므로 먼저) 상담 테이블·컬럼·인덱스·외래키 이름을 미팅으로 바꾼다.
4. 상담 상태를 새 `meeting_status`로 바꾼다.
5. 미팅·매물 상태를 새 규칙으로 다시 계산한다.

### 계약 잔금 (마이그레이션 `20261128100000_add_kkiru_contract_balance`)

- 계약에 **잔금(`balance`, 만원 정수)** 과 **잔금일(`balanceDueOn`, DATE)** 을 더한다. 둘 다 필수다.
- 잔금은 0 이상 정수, 잔금일은 계약 일자와 같거나 뒤여야 한다(DTO와 서비스 둘 다에서 막고 400).
- 계약 폼은 잔금을 보증금 − 계약금(음수면 0)으로 미리 채운다. 사용자가 잔금을 직접 고친 뒤에는
  보증금·계약금이 바뀌어도 덮어쓰지 않는다. 수정 화면은 저장된 값을 그대로 보여 준다. 서버는 받은 값을 그대로 저장한다.
- 계약 목록에 잔금·잔금일 컬럼을 두고 정렬할 수 있다(`sort=balance`, `sort=balanceDueOn`).
- 기존 계약은 잔금 = 보증금 − 계약금(음수면 0), 잔금일 = 임대차 시작일(없으면 계약 일자)로 채운 뒤 NOT NULL로 바꾼다.
  달력 조회를 위해 `contracts_balance_due_on_idx` 인덱스를 둔다.

### 기록의 관련 매물 (마이그레이션 `20261128110000`·`20261128110100`)

- 미팅 기록(`meeting_records`)에 **관련 매물(`listingId`, 선택)** 을 더한다. 일반 문의 기록은 비워 두고,
  어떤 매물에 대한 기록인지 남길 때만 고른다. 외래키는 다른 끼루 관계와 같이 `ON DELETE RESTRICT`다
  (끼루 매물은 지우지 않는다). `meeting_records_listing_id_idx` 인덱스를 둔다.
- 기록 추가·수정(`POST /admin/kkiru/meetings/:code/records`, `PATCH .../records/:recordId`)은
  `listingId?: uuid | null`을 받는다. 값이 있으면 그 미팅의 미팅 매물이어야 하고 아니면 400이다.
  수정에서 `null`이면 연결을 끊고, 보내지 않으면 그대로 둔다. 이미 연결된 매물은 그사이 미팅 매물에서 빠졌어도
  같은 값으로 다시 보내 그대로 둘 수 있다.
- 미팅 매물을 빼도(`DELETE .../listings/:listingId`) 그 매물을 가리키는 기록의 연결은 그대로 둔다. 기록은 이력이다.
- 미팅 상세 `records[]`와 계약 상세 `history[]`의 각 기록에 `listing: { id, code, name } | null`을 준다.
- 화면: 기록 추가·수정 폼에 '관련 매물'(기본 '선택 안 함', 선택지는 그 미팅의 미팅 매물)을 두고,
  미팅 매물이 없으면 칸을 숨긴다. 매물이 3개 이하면 칩, 넘으면 select다. 기록 목록과 계약 히스토리는
  관련 매물 이름을 본문 앞 회색 태그로 보인다.
- 기존 기록 이전: 내용이 `[매물 이름] `으로 시작하고 그 이름이 **그 미팅의 미팅 매물** 중 정확히 하나의 이름과
  같으면 `listingId`를 채우고 앞머리를 뗀다. 맞는 매물이 없거나 둘 이상이면, 또는 떼면 내용이 비면 그대로 둔다.
  이 이전으로 화면에서 앞머리를 나누던 처리(`splitListingPrefix`)는 없앤다. 그대로 남은 앞머리는 본문 글자로 보인다.

### 수입 (스키마 변경 없음)

화면 시안: `docs/design/kkiru-income-style-a.html` (시안 A, 카드형. 캡처 `docs/design/preview/A-토스식.jpg`).
사이드 메뉴와 상단 머리글은 시안 것이 아니라 앱 공통 레이아웃을 쓴다.

- **금액·기준**: 금액은 계약 수수료(`commission`, 만원), 기준 날짜는 잔금일(`balanceDueOn`)이다.
  오늘은 서울 날짜로 백엔드가 정해 응답(`today`)에 넣는다. 프론트는 첫 응답 전 기본 기간에만
  브라우저의 서울 날짜를 쓰고, 응답이 오면 `today`를 따른다.
- **확정수입** = 계약완료이고 잔금일 ≤ 오늘. **예정수입** = 계약예정 전부 + 계약완료이고 잔금일 > 오늘.
  계약취소는 금액·건수·목록에서 모두 뺀다.
- **API**: `GET /admin/kkiru/income?year=YYYY` 또는 `?month=YYYY-MM`(하나만, 연도 2000~2100),
  선택 `&mine=listing|client`(내 매물 = `isMyListing`, 내 손님 = `isMyClient`가 참인 계약만).
  기간이 둘 다 없으면 이번 달, 둘 다 있으면 400. 권한은 다른 끼루 API와 같다(`kkiru` 관리자 세션).
  응답은 기간(`period`), `today`, `mine`, 확정(`confirmed`: 금액·건수), 예정(`expected`: 금액·건수),
  구분별 건수(`counts`: `all`·`listing`·`client`, 기간 안의 전체 계약 기준이며 `mine`과 상관없다),
  기간이 속한 해의 월별 합(`months`: 월별 보기에서도 그 해 전체, 계약이 있는 달만,
  `confirmedAmount`·`expectedAmount`·`count`), 계약 목록(`contracts`: `incomeState`는 `confirmed|expected`,
  잔금일 오름차순, 같은 날은 케이스 번호순, 취소 제외, 페이지 없음)이다.
  `mine`은 합계·`months`·`contracts`에 모두 같은 조건으로 걸린다. 건수를 함께 세기 위해 백엔드는 그 해 계약을
  한 번 읽고 기간·구분은 메모리에서 거른다.
- **화면** (`/kkiru/income`, 카드형): 제목 줄 → 첫 카드(합계·흐름 막대) → 목록 머리(칩) → 카드 목록.
  - 제목 줄: '수입' + 오른쪽 월별|연간 세그먼트와 ‹ 기간 › 이동(2000~2100년 밖은 버튼을 끈다).
    연간 → 월별은 올해면 이번 달, 다른 해면 1월.
  - 첫 카드: 왼쪽 'N월 수입'(연간은 'YYYY년 수입') 큰 합계(확정+예정)와 확정수입·예정수입 두 알약
    (금액·'계약 N건', 0건이면 '없음'을 흐리게). 오른쪽 'YYYY년 흐름' 12개월 세로 막대(확정 아래·예정 위로 쌓기,
    보고 있는 달은 진한 brand, 호버·포커스 툴팁 'N월 X만원 / 확정 X · 예정 X', 막대를 누르면 그 달 월별).
    넓은 화면(xl)만 두 열이고, 그보다 좁으면 막대가 합계 아래로 내려간다.
  - 목록 머리: 'N월 계약 N건'(상태 필터 반영) + 구분 칩(전체 계약/내 매물/내 손님, 건수는 `counts`) +
    상태 칩(전체/확정/예정).
  - 월별 목록: 계약 카드 한 장씩(잔금일 날짜 배지·요일, 임차인·케이스 번호, 대상 매물, 구분 칩,
    수수료와 '● 확정'/'● 예정'). 카드 전체가 계약 상세 링크다. 순서는 잔금일순이고 정렬 조작은 없다.
  - 연간 목록: 계약이 있는 달만 카드 한 장씩(달 이름·건수·합계, 확정·예정 금액). 누르면 그 달 월별.
    상태를 고르면 그 상태 계약이 있는 달만, 그 상태 금액·건수로 보인다.
  - 상태 필터는 목록만 거른다. 합계·막대·칩 건수는 기간·구분 기준이다.
  - 빈 기간·조건 결과 없음·불러오는 중·오류는 같은 카드 모양의 짧은 안내로 보인다.
  - 주소: `?month=YYYY-MM` | `?year=YYYY`(기본 이번 달은 생략), `&mine=listing|client`,
    `&state=confirmed|expected`. 기간을 바꿔도 구분·상태는 유지한다. 잘못된 값은 기본값으로 본다.

## 대안 (Alternatives)

1. 테이블 이름은 그대로 두고 화면 이름만 '미팅'으로 바꾼다.
2. 옛 미팅 테이블을 남겨 두고 새 화면에서만 쓰지 않는다.

## 대안 기각 이유

1. 코드·DB 이름과 화면 이름이 어긋나 이후 작업에서 혼란이 크다.
2. 쓰지 않는 테이블과 상태 규칙이 남아 상태 계산이 두 갈래가 된다. 옛 데이터는 모두 새 구조로 옮길 수 있다.

## 영향 (Consequences)

### 장점

1. 미팅 상세에서 바로 계약으로 넘어가 단계가 하나 줄어든다.
2. 상태 규칙이 계약과 중단 여부만 보므로 단순해진다.

### 단점/리스크

1. 옛 미팅별 상태(특히 매물 하나만 진행중단된 미팅)는 미팅 단위로 합쳐지며 사라진다.
   옛 진행중단 미팅은 로그(kind=stopped)로만 남고 새 미팅의 `stoppedAt`은 비어 있다.
2. 옛 테이블을 지우므로 마이그레이션은 되돌릴 수 없다. 적용 전에 백업한다.
3. 옛 `/kkiru/consultations` 주소와 미팅 UUID 주소의 북마크는 더 이상 열리지 않는다.

## 비용 (Cost)

### 산정 기준

1. 추가 인프라 없음.

### 예상 비용

1. 월 고정비: 0
2. 월 변동비: 0
3. 월 합계(예상): 0

### 민감도/변동 조건

1. 해당 없음.

## 완화 전략

- 운영 DB 적용 전에 끼루 스키마를 백업하고, 적용 전후 건수(미팅·계약, 완료 계약 수수료 합)를 비교한다.
- 마이그레이션은 단계별 파일로 나눠 실패 지점을 좁힌다.

## 적용 범위 (Scope)

`apps/backend`의 끼루 모듈과 Prisma 스키마, `apps/backoffice`의 끼루 화면. OpenAPI 계약 문서는 범위 밖이다.

## 롤백/재검토 조건

- 미팅 하나에서 여러 매물을 동시에 계약해야 하는 업무가 생기면 결정 3(한 미팅 계약 1건)을 다시 본다.
- 매물별 방문 일시가 필요해지면 미팅 매물에 일시 컬럼을 더하는 것을 검토한다.
